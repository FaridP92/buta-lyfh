# Automatisations · n8n et Edge Functions

Principe repris des workflows Courant : chaque workflow écrit une ligne dans `automatisation_run` (début, fin, statut, message, lignes), porte une note collante (déclencheur, entrées, sorties, credentials par nom), et envoie un email Gmail à Frédéric après trois échecs consécutifs. Les workflows sont créés, validés (`validate_workflow`) et publiés via le MCP n8n, puis exportés en JSON dans `n8n/` à chaque modification. Le skill `n8n-workflow-architect` relit chaque workflow avant publication. Aucun secret dans les exports.

Filet de sécurité (migration 0028, 18 septembre) : tant que WF1 et WF2 ne sont pas publiés, deux tâches pg_cron dans Supabase rejouent chaque matin `buta.rafraichir_marts()` (04:05 UTC) et `buta.executer_controles(buta.journee_publiee())` (04:15 UTC), sinon les trois vues matérialisées prendraient un jour de retard sur les autres vues à chaque lever de journée publiée. Elles n'écrivent rien dans `automatisation_run` (le journal reste celui de n8n) et seront retirées (`cron.unschedule`) quand WF1 et WF2 seront publiés.

Règles : idempotence (rejouer WF1 le même jour ne publie rien deux fois ; WF4 fait des upserts) ; délais d'attente explicites sur chaque nœud HTTP (30 s, sauf le rafraîchissement des vues matérialisées à 120 s, mesuré à 20 s) ; pas de boucle sans borne ; un sous-workflow par département pour WF4 si la mémoire pose problème (leçon DVF Insights). Fuseau Europe/Paris sur l'instance et dans les réglages de chaque workflow ; délai d'exécution 10 minutes ; WF0 déclaré comme « Error workflow » de WF1, WF2 et WF5.

Les appels Supabase passent par le nœud HTTP Request avec le credential prédéfini « Supabase API » (en-têtes `apikey` et `Authorization` injectés par n8n, jamais écrits dans un paramètre), l'en-tête `Content-Profile: buta` pour les RPC et `Accept-Profile: buta` pour les lectures, et l'option « réponse complète » : le retour de la RPC est dans `body`, le code HTTP dans `statusCode`.

Publication d'avance : `buta.journee_publiee()` est plafonnée à la veille en heure de Paris (migration 0017) et `dossier_a_date` exclut les leads postérieurs. Publier d'avance jusqu'au 25 septembre (fait le 18 septembre : `npm run publier -- --jusqua 2026-09-25`, 1 061 dossiers) ne montre donc jamais le futur : `mart_fraicheur` porte la journée affichée (`date_reference`) et la date jusqu'à laquelle les dossiers sont publiés (`disponible_jusqu_au`), et la journée affichée avance chaque nuit même sans n8n. WF1 trouve alors « déjà publié » et se contente de rafraîchir les vues et l'heure d'intégration.

## 2. Edge Functions (Supabase, Deno)
### `analyste`
Entrée : `{ question: string, contexte?: { periode, agence } }`. Sortie : `{ statut: 'ok' | 'refus' | 'repli' | 'erreur', sql?, colonnes?, lignes?, reponse?, sources?, cout_eur, duree_ms, motif_refus? }` (même union pour `expliquer-ecart`, validée par Zod côté front).
Étapes : quota (5 appels par minute et 20 par jour par empreinte d'adresse hachée, 400 par jour au total, budget `IA_BUDGET_JOUR_EUR`, fixé à 5 € la semaine de l'entretien puis 1,5 €) ; classification de la question (périmètre, conseil, hors sujet) et génération SQL par le modèle en un seul appel, avec le catalogue des vues autorisées généré depuis les commentaires SQL (`buta.catalogue_analyste()`, IA.md §2) et les référentiels ; validation par `garde-fous.ts` (SELECT unique, CTE acceptée, aucun point-virgule ni commentaire, mots interdits, vues de la liste blanche seulement, schémas système refusés, `LIMIT` forcé à 200), une correction possible par le modèle ; exécution par connexion directe (`SUPABASE_DB_URL` injectée dans la fonction) dans une transaction `set local role analyste_ro`, `set local statement_timeout = '5s'` (le rôle ne lit que les vues `mart_`) ; rédaction de la réponse par le modèle à partir des lignes (le modèle ne calcule rien : s'il faut un total, il est calculé en SQL) ; contrôle que tout nombre de la réponse figure dans les lignes, à la reformulation d'unité près (`_partage/nombres.ts`), sinon la rédaction est rejetée et les lignes restent la réponse ; journal `analyste_question` et `ia_usage`. Modèle : Anthropic (`ANTHROPIC_API_KEY`, `IA_MODELE`), sinon Mistral (`MISTRAL_API_KEY`), sinon statut `repli`.
### `expliquer-ecart`
Entrée : `{ perimetre: 'reseau' | code agence, mois, indicateur: 'CA' | 'MARGE' | 'CONVERSION' }`. Étapes : lecture des faits dans `mart_ecarts`, `mart_funnel`, `mart_ventes_produit`, `mart_alertes` pour le périmètre ; prompt structuré (IA.md §3) ; sortie `{ constat, causes: [{texte, fait, source}], action, sources }` ; même contrôle des nombres ; cache 24 h par clé (périmètre, mois, indicateur, date de publication) pour ne pas payer deux fois la même explication.
Repli : si `ANTHROPIC_API_KEY` est absent ou le budget épuisé, `statut: 'repli'` et le front affiche les phrases par règles (`src/lib/phrases.ts`).

## 3. Journal et affichage
`automatisation_run` alimente l'écran Automatisations (50 dernières exécutions, durée, statut) et la ligne « prochaine exécution » calculée depuis le déclencheur. Statuts : `ok`, `deja_publie` (WF1, journée déjà disponible), `alerte` (WF2, contrôle bloquant KO ou score sous 90, email envoyé), `erreur` (WF5 quand le site ou l'API ne répond pas, WF0 pour tout workflow planté). Les lignes écrites par WF0 portent le début à l'instant de l'échec (durée nulle), n8n ne transmettant pas l'heure de départ de l'exécution en erreur. `ia_usage` alimente un compteur discret sur l'écran Analyste (« coût du jour : 0,23 € sur 1,50 € »).
